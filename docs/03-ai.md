# Where the AI is, and where it is not

Claude does four jobs in this system. All four share one shape:

> **The model reads a structured trace and returns a small structured judgement
> that a human or a deterministic guard consumes. It never chooses whether to
> contact a customer, never sets a safety limit, and never mutates the taxonomy.**

Model: `claude-opus-5`, adaptive thinking, structured outputs validated twice.

---

## The four jobs

| Job | Input | Output lands in | Effort | If the model is down |
|---|---|---|---|---|
| [Merchant alerts](#1-merchant-alerts) | A counted cluster of failing cases | `merchant_alerts` | medium | Deterministic title + the same facts |
| [Unknown-code triage](#2-unknown-code-triage) | Sampled tuples for a reason we do not know | `taxonomy_proposals` (pending) | high | The job reports it could not run |
| [Escalation briefs](#3-escalation-briefs) | One case's tuple, rationale and ledger | `escalations` | high | A brief naming cause, money, activity |
| [Ledger self-audit](#4-the-self-audit) | Failure buckets counted in SQL | A terminal report | high | Buckets ranked by money |

---

## What makes this safe rather than decorative

### Nothing is load-bearing

`ANTHROPIC_API_KEY` is **optional**. Every job has a deterministic fallback that
is a supported path, not a stub, and `ask()` returns a `Result` rather than
throwing — a failure downgrades the prose, never the recovery.

This matters more than it sounds. A ladder rung holds an Inngest step open; if a
Claude call could throw, "the brief is terse" would become "the escalation never
happened". So the timeout is short (25s, against a 60s function ceiling), the
retry count is low, and the row is written either way.

### The model never counts

Every number in an alert or an audit finding is a **SQL aggregate**, computed
before the call and passed in as fact. The prompts forbid introducing a figure
that is not in the input.

A model that invents "roughly 50 cases" in an alert a merchant acts on is worse
than no alert, and the fix is not a better prompt — it is not asking it to count.

### Severity is the policy's, not the model's

Whether a condition is `warning` or `critical` decides whether someone is woken
at 2am. That lives in a reviewed YAML table where it can be argued about, not in
a paragraph generator's judgement on the night.

### Every output is validated twice

The API enforces a JSON schema; the caller re-validates with zod. Output that
does not match is `invalid_output` and takes the fallback path, exactly as if
the model were unreachable. Prose parsed with a regex is how a model's off-day
becomes a malformed database row.

> **Schema gotcha, learned the hard way.** `output_config.format.schema` accepts
> only the *structural* half of JSON Schema. `maxItems`, `maxLength` and
> `minimum` are all rejected with a 400 — and because every job fails soft, that
> 400 was swallowed into a report that merely looked unconfigured. A unit test
> now walks all four schemas for forbidden keywords, and `npm run ai:smoke`
> proves the round trip.
>
> The same lesson applies to zod: a *tight* `.max()` on a string does not
> shorten the model's answer, it **throws away a good one**. Minimums are the
> quality gate; maximums are a runaway guard; fields that feed a display slot
> are clamped, never rejected.

### Provenance is visible

Every escalation carries `briefSource`: `claude` or `fallback`, with the reason
when it fell back. The console shows it as a badge and a running tally.

Without it, a completely broken integration and a working one look identical
from the outside — which is the cost of failing soft, and the reason this column
exists.

## 1. Merchant alerts

**The problem it solves.** `merchant_alert` used to fire with
`signal: 'ladder'`, `affectedCases` copied off the policy row, and
`amountAtRisk: 0`. The `merchant_alerts` table had existed since Stage 3 and the
dashboard had read it since Stage 5; nothing ever wrote a row.

**What is deterministic:** the cluster is a SQL query, the amount is a `SUM`,
the baseline is the merchant's own observed failure rate for that method over 30
days, and the alert fires on a **cluster** — one case failing is a case, not a
breakage.

**What Claude does:** turns a correct set of facts into a sentence a merchant
understands in five seconds. The facts alone read like a log line.

**The house rule, enforced in the prompt:** diagnostic, never prescriptive. We
say what broke and what it is costing. We do not say "disable UPI" — that is a
commercial decision that can cost far more than the outage, and a recovery agent
issuing operational orders is one bad paragraph away from real damage.

The identity of an alert is a structured key (`bank_not_enabled:ICIC:netbanking`)
rather than its wording, so a still-broken condition **accumulates into one row**
instead of paging once per case. Counts and prose refresh; `onsetAt` does not —
the merchant needs to know when this started, not when we last noticed.

## 2. Unknown-code triage

**The problem it solves.** A Razorpay reason with no descriptor lands on
`unknown_reason`, gets low confidence, and falls through to a cautious ladder.
That is correct, safe, and completely **silent**. A new code costing money since
Monday looks exactly like a quiet week until someone goes looking, and nobody
goes looking.

`npm run triage` groups the unknowns, samples their tuples, and asks Claude what
each one looks like — with the outcome evidence attached (how many of those
orders were eventually paid, by any route).

**The hard boundary.** Nothing here is ever applied automatically. The output is
a row in `taxonomy_proposals` with `status: 'pending'`, and **there is no code
path from an accepted proposal to a change in `codes.ts` or `diagnose.ts`.**
Accepting one means a person opens an editor and writes the rule by hand, with a
golden fixture, like every other entry.

That is not caution for its own sake. The taxonomy is the safety ceiling for the
whole agent — `sameInstrumentRetry` and `contactCustomer` are derived from the
cause class — so a wrong class there does not produce a badly worded message, it
produces **a customer's card locked at the issuer** after a third automated
retry.

The prompt reflects that asymmetry: bias toward the class that acts *less* when
the evidence is ambiguous, and `sameInstrumentRetrySafe` must be false unless
re-presenting could plausibly succeed. A `low` confidence answer with a clear
statement of what is missing is a good answer.

Below three occurrences nothing is proposed at all. A model asked to classify a
string it has seen twice will write a confident paragraph anyway, and a reviewer
will read it.

## 3. Escalation briefs

**The problem it solves.** `escalate_to_human` built an action, wrote a
`case_actions` row, and stopped. No queue, no notification, no UI, and the only
note on it was a static string copied out of the YAML — so every `risk_review`
case arrived looking exactly like every other one.

Building the queue fixed half. This is the other half: a queue whose entries all
say "escalated by ladder" is ignored within a week, and an ignored queue is
worse than no queue because it looks like coverage.

**Why a model, for this specifically.** The facts of an escalation are spread
across four tables — the tuple and rationale on `recovery_cases`, what was
planned on `case_actions`, what happened on `case_events`, what was said on
`message_log`. A human triaging has to reassemble that before they can think.
Everything needed is present and structured; what is missing is the sentence
that says what it means.

The brief has five fields: headline, what happened, what we tried, what is
blocking, and a **recommendation** — which is advice to a person who decides,
labelled as such everywhere it is displayed. Nothing automated reads it back.

The prompt draws the distinction that matters most in a ledger: *the agent chose
not to act* (a `rung_aborted`) versus *failed to act* (a `rung_uncomposable`)
versus *acted and it did not work* (a `rung_fired` that led nowhere). These are
completely different problems and the ledger says which.

Constraints carried into the prompt: never recommend contacting a customer who
opted out or already paid; never recommend re-presenting an instrument the
diagnosis ruled out; on `risk_review`, never suggest increasing pressure.

## 4. The self-audit

**The problem it solves.** The dashboard answers "how much did we recover?" It
cannot answer the question that actually costs money:

> **Which cases did we lose *without the agent ever acting*, and why?**

Those are the fixable losses. A customer who received three good messages and
did not pay is a customer who did not want to pay. A case that sent nothing
because its payment link could not be composed is a bug with a price tag.

This is not hypothetical. `run-ladder.ts` carries the post-mortem of one: a case
whose frequency cap cleared three hours out, deferred twice against a flat
one-hour guess, and abandoned 57 minutes early having sent nothing — "no trace
except four `rung_deferred` rows that all say the same thing". It was found by a
person reading the ledger by hand. `npm run audit` is that person, weekly.

**What Claude adds over a `GROUP BY`:** the counts are SQL. What the model adds
is the join a query cannot make — that forty `channel_deliverable` aborts and one
merchant's onboarding date are the same story, or that `deferral_limit` beside
`within_frequency_cap` means the cap arithmetic is wrong rather than the merchant
being busy.

The prompt insists on three things that make a report readable: rank by **money
and fixability** rather than raw count; separate our defects from merchant
configuration from working-as-designed (an abort on `order_paid` is the system
working and should be reported as such); and name a **specific next step** — a
file, a merchant, a query. "Investigate further" is not a finding.

An empty findings array is a valid and useful answer, and the model returns one
on a quiet week.

## Where Claude is deliberately absent

This is as much of the design as the four jobs above.

### Not in `compose.ts` — message copy

The Stage 7 plan said Claude would pick the template and fill the variables.
Building it made clear that is not true: **the intent already determines the
template, the language is a lookup on the customer's locale, and every variable
is a deterministic projection of the case.** There is no judgement left for a
model to make, and routing it through one would add latency, cost and
non-determinism to a function that is currently exhaustively testable.

WhatsApp template approval makes it moot anyway — improvised copy is unsendable.

### Not in `preconditions.ts` — the gate

A safety limit is a comparison. From the code:

> *A model that is right 99% of the time still double-messages someone once
> every hundred runs; a comparison does not.*

### Not in `diagnose.ts` — classification of known codes

44 documented codes with an exhaustive golden suite that brute-forces the entire
reason × source × step × method space already beat a model, and they replay
identically forever. The model's role in the taxonomy is limited to *proposing*
entries for codes we do not have, for a human to accept.

### Not choosing to send

No Claude output is ever an input to whether a message goes out, to whom, or
when.

## The bounded-autonomy argument

`core/actions/types.ts` defines a closed union — `nudge`, `create_payment_link`,
`retry_debit`, `merchant_alert`, `escalate_to_human`, `close_case`, `no_op` and
a few more. That union is the **entire vocabulary of things the agent can do in
the world**. The planner may only emit a value of this type. It never gets a
generic tool handle on the Razorpay API.

That is the whole of bounded autonomy: **not a prompt asking the model to be
careful, but a type that makes the dangerous thing unrepresentable.**

Adding a member is a deliberate expansion of what the agent may do, and is
reviewed as such.
